# Commerce UI/UX — storefront and model admin

## Storefront fixes · 26 October 2026

Product cards show one prominent photo-corner condition badge: **Mới / New** for the `new` unit, **2hand** for every other condition (including incomplete, defective and owner-defined conditions). The badge follows the unit whose price the card displays; if the main listing is sold out, the lowest-price available condition determines the badge. Condition uses a thin, tinted uppercase label at the top left; availability or the compact discount percentage sits at the top right. Neither uses a large solid block or a shadow. Outlet moves into the scale/metadata row, while free-shipping stays at the photo bottom, avoiding corner collisions. Labels keep a 22px height and 8px photo inset on desktop and mobile. The body retains the scale without repeating detailed condition chips. This is a storefront card presentation change only: condition data, product-detail selection/disclosures and Admin remain intact. Verification for the revised compact labels: production build/type checks, scoped ESLint and four VI/EN desktop/mobile browser scenarios passed. Checks cover incomplete/defective/custom conditions, available 2hand-only pricing, opposite-corner sold-out/sale badge separation, Outlet metadata and uniform card heights.

Monthly member-voucher eligibility is consistent between wallet, cart and issuance: active customer accounts (`USER`) can receive one code per month; Admin wallets do not advertise the customer-only claim. The cart also filters stale offers by the current role. Direct staff claims remain forbidden with the specific `MEMBER_CUSTOMER_ACCOUNT_REQUIRED` error and VI/EN guidance to use a customer account. Claim failures leave the picker usable without unhandled promise rejections. Verification: production build/type checks, server TypeScript compile, scoped ESLint, three isolated PostgreSQL checks (including concurrent/retried issuance and inactive accounts) and five browser checks across VI/EN passed. No live vouchers were issued by these tests.

Product detail now has a related-model shelf and compact secondary assistant/reservation actions. The Admin condition column no longer repeats quantities or sold-out captions; stock remains in its own column. See [Related product recommendations](product-recommendations.md) for retrieval, eligibility, ranking, failure behavior and limitations.

Product cards use a shared content rhythm: one tag row, two title lines, a brand row, a responsive price area, a compact availability area and a common action footer. Member/sale/plain/from prices and restock/view actions share the same alignment. Active restock feedback remains available to screen readers; failures stay visible. Product detail no longer repeats ratings below the title; the review tab remains. A three-column service strip near the purchase actions summarizes nationwide delivery, transfer/deposit plus COD balance, and returns subject to policy and disclosed condition. Verification: production build/type checking, scoped ESLint and eight browser checks passed (VI/EN, desktop/mobile), covering mixed card content, price/footer alignment, service-strip overflow, review counts below the product, existing tabs, filters and event hover. Narrow cards omit the secondary star row to keep the brand readable.

The Admin product table keeps condition badges and available-condition prices together. Status badges remain on one line; badges may wrap as whole units. Price/stock/sold columns use aligned tabular numbers, with stable minimum widths for stock and status. The existing table scrolls horizontally on smaller screens so data stays readable in normal and compact row modes. Verification: production build/type checking, scoped ESLint and six browser checks (VI/EN at 1440, 1024 and 390px), including stock sorting and compact rows, passed.

Product information tabs show counts as quiet inline text. On mobile, all three tabs fit the row with wrapping labels; active state uses text weight and colour rather than a second underline. Keyboard navigation and visible keyboard focus remain available.

Catalog filters use four compact selects (including the owner-configured conditions), stock availability and one price control. The repeated hint/reset footer and nested refine section are removed; clear/remove actions remain beside applied filters. The sidebar scrolls with the page rather than creating its own scroll area. Product cards share the same surface and hover on home, catalog and sale-event pages; hovering changes the border/shadow without lifting the card.

The profile sidebar no longer repeats the wishlist destination. The address book prioritizes saved recipient cards and opens an editor on add/edit, with a folded optional map. Existing address validation, create retry identity, optimistic versions and the 20-address limit remain. Saving locks editable controls; uncertain responses retain the draft, and deletion requires confirmation. Browser verification intercepts every write, so no shop addresses are modified during UI testing.

Verification: production Next build with `--no-lint`, TypeScript and scoped ESLint pass. Eight new VI/EN laptop/mobile browser cases cover the requested fixes; storefront regression checks cover condition selection, filters, cart/gallery navigation and public catalog rendering. The full suite is not green: existing Admin fixtures omit the now-required target price S and still expect the retired issue-count pricing input. These fixtures and pricing behavior are left unchanged in this UI work. Two storefront navigation checks passed when rerun after transient retained-DOM/navigation failures.

## Admin workspace

The shared breadcrumb component now supplies only a screen-reader heading. The visible page heading and breadcrumb row have been removed across admin; the global header still identifies the current destination. Obsolete heading styles have also been removed.

The model editor no longer repeats the model photo, name, SKU, price and stock in a summary sidebar, or the extra ID/sold caption. A condition option retains its useful link to the parent listing in a compact notice.

The condition tab now starts with a listing table: SKU/photo, condition and disclosed issues, aligned selling/list prices, stock, actual archive/inventory status and a labelled edit action. A current-listing marker identifies the form below. Edit links open the exact unit directly in the condition tab; the current row's edit button focuses its form. Add-condition keeps the existing validation, image upload and API flow. The small stock summary belongs to this tab and sums non-archived listings, including zero-stock conditions; archive rows remain visible in the table. It does not claim warehouse movements or a separate inventory source. On smaller screens it stacks below the table, which scrolls horizontally inside its own labelled region.

The model-level catalog keeps its existing grouping, search, filters, sorting and column preferences. Its condition column now separates each condition's badge, stock count and lowest in-stock selling price, so staff can compare conditions before opening the model.

The catalog and inventory statistics remain peer tabs. The editor retains its identity, condition/options, images, pricing, inventory/packaging, descriptions and supplier/display tabs. Draft values survive tab changes. Validation opens the affected tab and focuses its invalid field. Save, discard and delete remain visible in the workspace footer. The creation wizard retains its step validation and navigation.

Catalog, editor and creation workspaces reclaim the space previously reserved for headings. Copilot moves into the existing global header on model pages, with an icon button on narrow screens; it retains its dialog and record context.

## Implementation

`WorkspaceTabs` retains labelled tablists, matching tab/panel IDs, selected state and roving tabindex. Arrow keys, Home and End navigate between retained panels. `compact-workspaces.css` now contains only the shared tabs and admin geometry. Vietnamese and English remain supported.

Admin theme tokens now have one owner in `admin-workspace.css`, shared with portaled dialogs; competing Collector Studio token declarations have been removed. ## Product input audit — 25 October 2026

The create wizard, product editor and add-condition dialog share the same field contract. The inventory tab follows this order: SKU/available quantity/received date, shipping package measurements, then descriptive metadata. The basic-information tab puts the product name first, then brand/model code, then category/scale. Pricing inputs precede the calculated outputs; descriptions follow Vietnamese, English and common fallback order.

| Fields                                                | Control                        | Ownership and rules                                                                                                                                                                                                                                                                                                                         |
| ----------------------------------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Name, brand, model code, scale                        | Text                           | Model identity. Name and brand are required; brand/scale remain open text because the API accepts custom values. Inherited text is read-only and copyable on a condition option.                                                                                                                                                            |
| Category, supplier                                    | Select                         | Choose existing records; optional empty value is preserved. Disabled on an option because the server inherits these from its main listing.                                                                                                                                                                                                  |
| Condition, assembly, inventory status                 | Select                         | Existing enum values, with explanations. An existing pre-owned item's condition is locked to match the server's unique-item identity rule. Assembly and inventory status remain unit-specific.                                                                                                                                              |
| Descriptions, condition notes, accessory/defect lists | Textarea                       | Shared labels, hint/error links and unique IDs. Lists use one item per line; missing accessories/defects are required for their respective conditions. Model descriptions are read-only on options.                                                                                                                                         |
| SKU, quantity, received date                          | Text / whole number / calendar | Unit-specific fields stay editable. Quantity is non-negative; pre-owned quantity is at most one and cannot be increased beyond saved stock in this form. Typed dates use the same strict parser as the calendar (invalid rollover dates are rejected).                                                                                      |
| Reference price, cost, issue count                    | Whole-number input             | Explicit VND units without separators; issue count is 0–100 and stays disabled until a reference exists (without a reference the payload retains the legacy price and does not submit an issue count). Derived prices remain labelled text outputs, not editable inputs. Existing legacy prices are retained when no reference is provided. |
| Shipping length/width/height, weight                  | Whole-number input             | Shared model data: 1–200 cm and 1–50,000 g. All four empty retain the shop default; otherwise all four are required. Per-field validation matches the existing server parser. Read-only on options.                                                                                                                                         |
| Descriptive weight/dimensions                         | Text                           | Stored independently from shipping measurements; never silently overwritten. The separate section explains which data calculates shipping. Inherited and copyable on options.                                                                                                                                                               |
| Main image / gallery                                  | File picker                    | The main editor requires a main image. Condition-option controls retain the listing-photo fallback; the existing server evidence requirements remain authoritative. Replace/upload actions remain keyboard-focusable; image errors point to the file control.                                                                               |
| Fragile/orientation, archived/featured                | Checkbox                       | Binary controls. Packaging flags are inherited and disabled when no custom package measurements are entered; listing status flags remain editable.                                                                                                                                                                                          |

Required controls expose native `required` semantics with a visual marker. Numeric inputs retain invalid negative/decimal values for correction instead of stripping characters (`30.5` must not become `305`). Errors identify and focus the actual input. Fields with the same name in the editor and a modal have unique label/error IDs. Saving disables the editable fieldset and conflicting actions until the request finishes; the option dialog also prevents closing mid-request. `product-forms.css` owns the consistent editable/read-only/disabled/error appearance.

The shared field-ID change also preserves password-recovery focus by querying its own form, rather than assuming a global email input ID. Recovery browser checks intercept the reset request; no email is sent.

Input-audit verification completed: all 12 unit cases and all 48 browser cases passed, with the browser cases passing together in the final run. Coverage includes whole-number/range/date validation, independent descriptive and shipping payloads, inherited/read-only/disabled states, dependent packaging/pricing controls, request-in-flight locks, unique editor/modal labels, required and keyboard-accessible image pickers, and recovery focus. Vietnamese/English, desktop/mobile and both themes were checked. Targeted ESLint and the optimized Next.js build with type checking passed; the existing full-project lint-plugin limitation described above still requires `--no-lint` for the build. No backend, database schema, dependency or real business data was changed.
## Bổ sung luồng bán trực tiếp (25/10/2026)

Admin → Đơn hàng có nút **Tạo đơn bán trực tiếp** và bộ lọc nguồn Website / Tại shop / Chat–điện thoại. Desktop rộng dùng ba vùng chọn hàng, khách hàng/giao nhận và thanh toán; mobile xếp theo thứ tự thao tác. Tên/SĐT tùy chọn khi nhận ngay, bắt buộc cùng địa chỉ khi giao hàng. Giá là dữ liệu server; số lượng bị giới hạn theo từng SKU. Tải lại cập nhật cả giá/tồn của hàng đã chọn và yêu cầu xác nhận lại tiền thực nhận.

Khoản thu tiền mặt dùng nhãn phiếu thu; khoản thu trước và hoàn tiền không gắn nhãn chuyển khoản cho giao dịch tiền mặt. Không hiển thị cảnh báo COD chưa thu cho đơn đã thanh toán. Đặc tả, schema, giới hạn và kiểm chứng: [Bán trực tiếp và đơn chốt ngoài website](../business/direct-sales.md).
